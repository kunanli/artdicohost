# 云端隔离合成验收

本模块补足「程序已发布／账号已配置」与「私有储存及实际操作已验证」之间的验收路径。当前实现与本机测试不等于已取得云端结果；正式结果必须由固定香港函数的签名健康入口读回。

## 控制入口与执行边界

生产环境由受控配置程序设置唯一非秘密标识 `ARTDICO_CLOUD_ACCEPTANCE_RUN_ID=r<GITHUB_RUN_ID>-a<GITHUB_RUN_ATTEMPT>-<16位随机hex>-<完整源码SHA>`。执行次数与每次控制器调用的新随机值防止重跑时复用旧实例的通过证明；末尾源码必须绑定正在执行的 `release.json.sourceCommit`。同时要求内容开关精确为 `false`、固定本站 bucket／region／origins、production 模式及 FC 平台的三项临时角色凭据。不使用 GitHub 部署 AccessKey 读写私有对象，也不把临时身份取回 runner。

验收仅在 `createProductionCloudServer` 构造时启动一次，在后台执行；读取健康状态不会重跑任何写入。设置存在时生产业务运行时一律保持关闭，即使内容开关被错误设为 true；错误配置产生 rejected 结果，不执行储存请求。关闭标识后恢复常规关闭状态；业务启用必须另行受控、明确移除验收标识，不能仅设置内容开关。

无访客验收路由、命令执行路由或测试账号。原 `defaultTrigger` 继续使用 FC 签名认证，独立自定义域名路由继续排除 `/healthz`。不得为取得验收结果把 trigger 改匿名或增加全站路由。

`GET /healthz` 仍以 `scope: process-only` 描述进程健康；仅在启用上述控制标识时增加 `acceptance` 的固定白名单投影。包含源码、run ID、随机进程标识、running／passed／failed／rejected、已完成阶段、请求与触及对象数、两个独立客户端及一个 FC 进程的事实。不会返回账号、密码、摘要、Cookie、CSRF、对象正文、对象 key 或提供者错误。当前配置控制器与实际云端运行由后续集成单独记录。

## 隔离与储存范围

每个进程随机生成 128 位标识，将全部 logical `cms/v1/{content,contacts,portraits,sessions,limits,probes,registrations,registration-reviews,intent-invitations,group-invites,users,maintenance,restores}/...` 映射到 `cms/v1/acceptance/<run-id>/<instance-id>/...`。适配器拒绝不认识的类别、已经 scope 的 key、路径穿越、重复分隔及不合法 run ID。正式运行路径不变；会话、全局登录额度及照片与内容一起隔离，不消耗正式工作人员的额度或读写其资料。隔离恢复也只能写入相同 acceptance 前缀。

这一前缀位于现有专用角色的 `cms/v1/*` GetObject／PutObject 范围，不需要新增 IAM；它是应用层隔离，并非 RAM 强制隔离。没有列举或删除 API，不建立新 bucket、函数或其他云服务。

## 十项验收

1. 合成对象的 immutable 写入、独立客户端读取及 SHA-256／实际 bytes 核对。
2. 两个独立 journal 客户端从相同游标竞争，只有一个成功，另一项明确 409，重读只保留胜者。
3. 内存生成的合成工作人员以用户名及邮箱登录，匿名／错误密码／缺 CSRF／错误 Origin／无发布角色均拒绝。
4. 合成私密联络人保存与独立 store 回读，没有名单角色与匿名访问被拒绝。通过同一维护 API 将当时仅有的联系人 journal 加密备份、核对 hash、以原子 claim 隔离恢复并读回修订及完成审计；不切换线上状态或声称独立保存。v2 名额完整历史恢复另由专门合成回归验证。
5. 合成图片上传、内容保存及发布；公开投影无备注、身份凭据或联系人；相同修订竞争只有一个胜者；重建组件读回，撤回同意并发布后旧公开照片 URL 返回 404，私有保留独立处理。
6. 真实 append 后以受控 shim 丢弃 ACK，写入调用必须失败且不能重送；独立只读回查证明实际版本。该案例是受控 ACK 故障注入，不能称为观察到了真实网络丢包。
7. 正式报名合成政策及共用容量三位、合成预留一位，公开别名／CORS、令牌、同键竞争重放与内容冲突；一名公开报名、来源联系人转换和一名明确授权的工作人员共同占满三位，再保存一名候补且没有群码。来源分别保持 public／staff_assisted／staff_entry，代录没有伪造公开同意。已登记团队不新增匿名席位；同一受控 API 完成一份合成手动邀请批次准备，准备不等于发出或送达。
8. 审核角色拒绝、最小导出与审计、确认撤回后釋出名额并按顺序补位；原收据／旧群码拒绝，候补以原键回读后获得确认状态；任务页面拒绝 editor，已授权读取没有秘密与私人联系字段；删除待办准确回报未擦除。工作人员目录不返回摘要，bootstrap 账号不可覆盖。额外账号建立／停用及来源转换重复等既有行为继续由独立回归覆盖，不在本次 1000 请求中重复扩展。
9. 另一 auth／API 组件执行退出，原组件不能继续使用旧 Cookie；两种登录标识的会话均持久撤销。
10. 在当前隔离限流 journal 完整校验后，以真实 OSS CAS 单调准备到剩一额度；不存在账号的真实失败登入必须消耗最后额度，另一客户端的正确邮箱／密码及未知账号都必须返回实际 429 与正整数 Retry-After。产品默认十次／十五分钟与真实时钟不变。若过程确实正向跨一个窗口，最多重新准备一次；跨窗口实际成功的 200 不能充作 429 证明，第二次跨界或同窗口意外状态均失败。

整体期限 90 秒，最多 1000 次真实对象 HTTP 请求。任何阶段不明、超时、权限错误或对象异常均失败，不回报 passed、不打印原始错误、不盲重试未知写入。只有十项依序完成才能产生 passed。提供者权限拒绝的本机测试是故障注入，不能替代真实 IAM 策略／缺权限现场验收。

2026-10-21 导航发布在 02:14:59 UTC 武装验收，刚好跨 02:15 限流窗口，旧的逐次耗尽准备多写约四次 journal，实际以 9/10／1000 请求／83 对象失败。合成 fixture 的注销后换窗精确重现；同一准确 main 的受控 attempt 2 已恢复服务并完成 23 个 HTTPS 回读，见[发布证据](navigation-release-2026-10-21.md)。新有界准备不删减其他阶段、完整备份或提高请求／时间上限；仅写本次随机隔离前缀，不操作正式限流资料。`cloud-acceptance.test.mjs` 覆盖注销后、准备后、两客户端之间、已知与未知 429 之间的换窗，以及连续换窗有界失败；直接使用未覆写的 auth 验证默认十次／十五分钟与跨窗口复原，防止准备常量漂移。该修复已由 PR #32／main `b51dff2` 的正式运行 39533411247 验证：808 项检查、十阶段私有 OSS、300 人政策及 23 个 HTTPS 对象通过，10:38:35（UTC+08）完成。

控制器在失败及等待超时时，只附上准确源码／run 的已验证状态、下一个固定阶段、完成阶段数和 0–1000 的请求／对象计数；格式异常时省略诊断，不输出整个健康证明或提供者正文。请求计数在每次实际 `fetch` 调用前增加，包含 immutable 对象的前后回读；对象客户端没有 SDK 自动重试。963 次本机 fixture 不证明新版在真实云端可于 90 秒内完成，实际延迟、权限及服务行为须由这次云端有界验收确认。

首次实际云端运行 [39455839350](https://github.com/kunanli/artdicohost/actions/runs/39455839350)（源码 `8d17a700b78f430a3b3a9b337134a18b7abbed48`）完成前三项，在 private-contacts 阶段以 108 次请求／19 个对象失败，保持关闭并跳过公开部署。合成请求序列把该位置定位于首个较大联系人 JSON 的 PUT 后 GET 回读；固定时钟及前进时钟 fixture 都能通过。真实 Node fetch 测试确认默认压缩协商会解压正文，却保留压缩长度与 encoding，不能用于严格储存字节核对。因此 OSS 请求明确发送 `Accept-Encoding: identity`，仍拒绝服务端忽略协商所返回的编码正文；新云端运行通过前不将这一修正视为线上成功证据。

两个独立客户端、组件重建和 OSS CAS 不是两个真实 FC 实例。结果明确 `independentClients: 2`、`fcProcesses: 1`；跨 FC 进程的协调验收还须独立取得可核对的实例证据，不能由本结果自行推论。

## 验证、保留与回退

`node --test tests/cloud-acceptance.test.mjs tests/cloud-http-server.test.mjs tests/cloud-production-entry.test.mjs` 使用隔离合成 OSS HTTP fixture。早期仅内容的 fixture 为 323 次请求、37 个触及 key；新版包含名额／候补／工作人员／团队／批次邀请及早期联系人维护的十项 fixture 为 963 次请求、78 个触及 key，均不是线上证据。测试同时覆盖越界拒绝、源码／配置门禁、不会执行的配置、故障及全局期限、健康投影不泄露敏感额外字段、健康读取不重跑、生产 factory 遇验收标识强制关闭，以及原 HTTP／生产入口回归。`registration-admissions-backup.test.mjs` 另覆盖 v1 只读解释与完整 v2 历史、团队、工作人员原件的加密隔离恢复；实际早期维护阶段不能替代这项 v2 全历史证明。

验收对象含合成会话、已撤销会话、照片、快照和审计；全部留在私有 acceptance 前缀，结果精确记录 `cleanupPerformed: false`。没有删除权限也没有假清理承诺；保留、清理与独立备份维护流程须由运维工具覆盖，不能只删除当前日志破坏引用。

失败时保持内容开关 false，先读签名健康的固定阶段结果；不要导出完整函数环境或请求日志。回退先移除验收标识并保持内容开关 false，再按正常发布流程恢复上个已验收代码；保留合成对象用于诊断，不扩大运行角色权限。未通过维护与业务验收前，不以配置成功或进程健康代替真实可用后台。
