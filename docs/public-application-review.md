# 学生类别、精简申请与人工审核：下一阶段计划

这是用户已授权但尚未实施的下一阶段；先完成 [PR #36 实际部署](people-release-2026-10-21.md)，再开始代码。用户最新决定为防恶意报名而人工审核，覆盖先前提交后立即寄正式邀请的说法。

## 申请与名额

- 所有新公开申请（包括仍开着旧表单的客户端）由服务器强制进入 `pending_review`，不占共同 300 名额、不进入候补自动递补。报名期限与最多 1000 份已登记记录限制仍由服务器执行；不能让客户端关闭审核。
- 旧 v1／v2 confirmed、waitlisted、withdrawn 与不可变报名原件保持原语义。采用 v3 帐本容纳 pending_review／rejected 与 approve／reject 审计，原人项结构不扩张；v1／v2 只在内存解释，下一次明确 CAS 操作才存新版本，不在 GET 迁移。不得回退不认识 v3 的旧写入者。
- 在既有名额 API 新增明确的审核通过／不通过操作，reviewer／superadmin 在私有 I/O 前校验、Origin／CSRF／原修订／operationId 保留。通过只能处理待审申请；同一次 CAS 先分配既有已核准候补，再给新核准者分配 confirmed 或启用候补时的 waitlisted。满额且关闭候补则冲突、保持待审，不能超卖。审核可在停止收新申请后继续进行。
- 不通过保存为 rejected，保留原件及决定者审计；不等于本人在联系人档案回复婉拒。已撤回／拒绝者不被自动恢复。现有 review.status 是内部意见，与本次权威名额决定分开显示，不能靠下拉写 approved 获得名额。
- 失回执不自动重试／发信；保留同一正文、operationId 和修订，由工作人员明确确认同一操作。重播读当前状态，不能以历史批准把已撤回者复活。

## 精简表单与学生

一般申请为单页，必填姓名、Email、身份（含学生）和主动隐私同意；学校／组织、城市、微信选填。分享主题是同一申请内的可选项，只再问题目与简介；没有第二份会重复占位的报名，也不把固定「还缺两位」当自动席位库存。展位、住宿、其他合作在后台沟通，未问答案省略，不能伪填「不需要」。

保留旧完整表单校验；新精简资料使用显式版本标记及严格白名单，后台名单读取同时识别新旧记录，未知类型仍拒绝。学生加入身份枚举与筛选，不改原 Excel 九栏位置映射，不按学校推断。联系人当前 profile.categories 可明确编辑为选项数组，原 sourceProfile／摘要／来源答案保持不变；字串与数组序列化分开，旧客户端省略保留，导出分别保留原始与当前身份。学生不是自动工作人员、讲者、作品或展位职责。

## 私人收据与通知

公开提交仅返回「申请已收到，待审核」和私人查询／友善打印入口。pending_review 不建立正式通知 outbox，不提供入群码、邀请函或 Wallet；避免先占用初次确认通知的幂等键。GET、重开收据、列表与审核意见保存都不寄正式信。

真正核准 CAS 回执成功或同一操作重播后，才读 fresh confirmed 并调用既有 EmailJS／持久去重。核准但候补不寄正式邀请，日后实际转正再寄。原通知历史与 unknown 永不盲重送规则保留；邮件失败不撤销已核准名额，页面分开显示审核／名额与通知结果。用户新版个人 PNG 下载入口与字体在本阶段发布后继续实施，不能遗失该后续。

## 分工与验证

领域负责 v3／保存／审核／并发；API 与通知负责边界和发信门槛；公开表单负责新旧校验及精简 UI；后台负责人负责审核动作和学生人员编辑；消费者负责人负责个人页、志愿者、邀约／待办／Wallet／Excel 状态。root 装配 runtime、完整备份／隔离验收、来源包及实际发布；浏览器独立使用合成数据验证。不新增云资源、IAM、DNS、journal、费用、生产依赖或凭证。

验证包括未审零席零信、旧状态不倒退、两个审核争最后一席、已核准候补优先、关闭候补时满额冲突、审核意见不授予名额、同操作重播／失回执、拒绝／撤回、未知邮件不重寄、群码／Wallet／排班严格 confirmed、学生原件保留／旧问卷映射、新旧申请混合读取及完整备份重启恢复。真实 OSS 固定十阶段／1000 请求／90 秒边界保持，修改既有验收情境而非无界追加操作。准确 PR／main 与 HTTPS 回读通过后记录证据，再进入邀请函阶段。
