# ARTDiCO HOST 改版實作步驟

本計畫依 P0 → P6 執行；一次完成一階段的修改、必要檢查與交付證據，再進入下一階段。核心為「一人一個工作入口、多份原始來源保留、一個有效名額、一個私人參會頁」。狀態總表與本輪決策見 [改版入口](README.md)，實際工作人員操作見 [操作流程](02-staff-and-attendee-runbook.md)。

P1 至 P3 已完成程式交付並實際發布，最新證據見 [P3 紀錄](p3-release.md)；目前接續 P4，實作及待驗證範圍見 [P4 紀錄](p4-release.md)。既有能力以近期程式與 [統一人員流程](../unified-people-workspace.md)、[10 月 31 日體檢](../health-2026-10-31-admin-wallet.md) 為準；早期文件中的「純演示」「尚無 Apple 憑證」不是當前結論。

## P0 核對基準與準備執行

1. 核對 `git status`、工作分支、遠端 main、最近發布與尚未合併修改。本次文檔基準已快進至 `d583e4de9ae1676822c6ea6da984211099f73dd3`，包含 `FrontEnd_Resource`；開工時仍重新確認，不用舊工作區覆蓋新素材或程式。
2. 以最新 main 建立本階段分支，保留使用者未提交修改。讀取最新 `AGENTS.md`、[總實施計畫](../implementation-plan.md)、[接續台帳](../session-recovery.md) 和本階段契約；重用既有架構，不帶入 IGDA 正式資料、憑據或資源。
3. 逐項建立素材對應清單：原檔、用途、既有穩定 ID、衍生尺寸、公開狀態。素材來源為 [FrontEnd_Resource](https://github.com/kunanli/artdicohost/tree/main/FrontEnd_Resource)；上傳的照片或 Logo 不自動建立人物、確認出席或改變組織身份。
4. 確認執行環境的 Node／pnpm 與鎖檔，沿用既有 FC 自訂 runtime 包。記錄目前包限制與實際大小；不為本輪新增雲服務、IAM、DNS、資料庫或付費依賴。
5. 準備合成資料涵蓋舊意向、網站申請、多人場次、兩類作品、超過十五個位置與各名額狀態。正式名單不得用作測試夾具。

**交付條件：**本輪文檔交付先固定基準、決策及測試入口。P1 開工時建立階段分支、補素材清單及合成夾具；真實 ID 尚待核對者可先留空，不阻塞合成實作。Email 與 Wallet 沿用已配置的受控設定。P0 不執行正式名單匯入、合併、核准、發信或發布真實內容。

## P1 先完成相容資料契約

此階段先讓資料與公開投影可靠，再讓新介面使用；可依相依順序分成 P1a／P1b PR。

開始與交付時使用 [資料契約 Skill](../../.agents/skills/artdico-contract-check/SKILL.md)，並以 [旅程 Skill](../../.agents/skills/artdico-journey-check/SKILL.md) 記錄現行合成基準。Skill runner 只覆蓋其明列的既有案例；新功能仍需按本階段驗收補足測試。

### P1a 兩類作品與可新增展位

下列範圍已發布於 main `7d25921`。內容／儲存格式仍為版本 1，非持久化安排總覽改為版本 2；操作人員須重新載入舊分頁。寫入超過舊位置範圍的資料後，只能使用至少相容 P1a 的版本回退，詳見 [交付與回退步驟](p1a-release.md)。

1. 新建／重新分類只提供「学生作品」「独立游戏」。學生製作的獨立遊戲預設優先歸學生作品，其他舊資料由編輯者逐筆核對。
2. 保留舊 `kind:'team'` 及未填 `kind` 的讀取能力；不在 GET、部署或登入時批次改寫。舊團隊資料不得全部自動改為獨立遊戲。若前台需暫時呈現未歸類舊作品，可保留於「全部作品」並標示待分類，兩個分類選項維持不變。
3. 改版需同時涵蓋共享 schema、公開顯示、後台編輯、草稿恢復與發布比對。`public-content-refresh` 驗證整份公開快照，不能因刪掉舊枚舉讓所有公開內容失效。
4. 展位以實際記錄／位置產生清單，移除固定十五格的產品規則、補齊按鈕與文案。同步調整保存驗證、編排器、安排總覽回應及前端回應驗證，保留穩定 ID、編號唯一、位置衝突與取消歷史。
5. 沿用有界資料量與請求限制；「依需求新增」不代表解除所有技術上限，也不增加共同參會名額。既有未指定位置、同展位多作品與多位聯絡人繼續有效。

**主要檔案：**`shared/content-schema.mjs`、`shared/showcase-display.mjs`、`shared/arrangement-overview.mjs`、`src/lib/content-local-drafts.mjs`、`src/lib/booth-slots.mjs`、`src/lib/arrangement-planner.mjs`、`src/scripts/arrangements-view.mjs`、`src/components/ContentWorkspace.astro`、兩個內容 store。

### P1b 出席證明 公開人物與活動事實

下列範圍已發布於 main `535d3ed`，最終測試、準確來源包及實際發布證據見 [P1b 交付紀錄](p1b-release.md)。

1. 公開嘉賓區只列實際答應出席者。本人出席回覆、資料確認、正式名額與公開設定分開保存；`guest.status:'confirmed'` 不當作出席證明，缺少關聯或讀取失敗也不當作已出席。
2. 在 API 授權後核對已保存的人員關聯與最小出席證明，明確記錄來源修訂。瀏覽器不得讀取私密 contacts 來自行篩選；公開回應不包含 contactId、Email、微信、聯絡許可內容或內部備註。
3. 發布會跨內容／人員來源讀取，須偵測核對後來源變更。來源衝突或不可用時拒絕該次新發布並保留原快照，不宣稱跨兩份 journal 原子一致。publisher／editor 沒有邀約權限時，不因此取得整份私有名單。
4. 保留凍結公開快照的舊格式與原 bytes。新出席展示證明採相容的可選投影／明確版本契約，沒有證明的舊人物不推定到場；下一次由工作人員保存、核對與發布才建立新版本。新版嘉賓區在取得證明前不將舊人物列為確定出席，必要時顯示「出席嘉宾陆续公布」，其他公開內容仍照原快照讀取；不為補證明偷偷讀 contacts 或改寫舊快照。
5. 嘉賓區資格與日程講者呈現分開。新增最小公開場次參與者資料，支援主持、講者、圓桌嘉賓等已核對角色，保留舊 `guestId`。取消／待定／更換講者要有明確文案，不因全域過濾而意外清空整場。
6. 私人回覆變更後提示「需更新前台」，連結到相關嘉賓與場次核對；普通保存不暗中發布全部草稿。
7. 定義同一份已核實活動事實供首頁、私人頁、通知與新票券使用。當前確認服務從 `eventConfig` 取得事實，不能只改公開首頁就聲稱其他入口同步更新。允許以發布前一致性檢查作過渡，衝突時停止新通知／新票券並顯示待核對；舊 Email 與已存 Wallet 不自動改寫。

**主要檔案：**`shared/content-schema.mjs`、`shared/guest-display.mjs`、`functions/content-api/store.mjs`、`functions/cloud-content/store.mjs`、`functions/cloud-content/runtime.mjs`、`functions/person-workspace/`、`functions/registration-confirmation/service.mjs`、`functions/apple-wallet/service.mjs`、`src/lib/public-content-refresh.mjs`。

**P1 驗收：**舊快照完整可讀且讀取不寫入；舊客戶端漏傳保留新增欄位；新展位超過十五個位置可保存並載入總覽；出席未知不展示為確定；取消／跨來源衝突不誤發布；多人場次與舊主要講者連結仍有效；公開投影不洩漏私人欄位。

## P2 整合單人工作頁與舊意向工作佇列

下列程式範圍已由 PR #51 發布於 main `e531a3b`，完整回歸、公開／FC 建置瀏覽器及來源包證據見 [P2 紀錄](p2-release.md)。實際同事的操作觀察仍待執行，不以合成測試代替。

1. 重用已有統一名單、`personGroups`、人工重複核對、來源轉換與共同名額服務，不新增第二套人員／去重系統。
2. 單人工作頁集中必要操作。首屏只顯示目前資料、簡短明確狀態與一個主要下一步；出席回覆、名額、通知及公開以緊湊摘要呈現，原問卷、來源、歷史與完整安排按需展開，不做四張大型狀態卡或重複教學文字。
3. 同一名單預設顯示「待处理」，提供搜尋與「全部」切換；「待回覆」「待整合」「疑似重複」「待通知」作篩選條件，不增設多套工作頁。它們由既有事實投影，不另造互相衝突的完成狀態。主列表聚焦姓名／機構、當前狀態與下一步，次要操作收進詳情或更多。
4. 對舊資料先提供唯讀整合預覽；同名或同信箱只作線索。工作人員明確選主記錄後才沿用既有合併動作，保留原件、許可、通知與歷史。合併不自動核准待審、不復活撤回、不在合併時發信或晉升候補。
5. 只有「預計參加」者先跟進；已明確答應者沿用原來源整合名額。存在網站申請時沿用其主記錄與原審核結果，不要求重填、不另占一席。
6. 舊住宿需求與演講題目保留在原回答及待跟進事項，新簡表沒有詢問不代表「不需要」。既有演講資料只補缺項，原興趣不自動授予講者身份。
7. 信箱變更、聯絡許可未知／拒絕、未知通知結果各自顯示原因；不靠改目前聯絡卡或合併另一份同意繞過原通知限制。私人連結僅在授權的單人操作取回，不放進列表、暫存或 Excel。
8. 所有編輯沿用單一「保存」與精確回執，一般保存不加確認彈窗；成功後留在同一人、同一位置並保留輸入與焦點，只在附近顯示「已保存」。核准、合併、寄信、交付連結和公開發布各自保留明確動作與結果，但只突出當前適用的主要動作。合併、撤回及發布影響以精簡預覽說清楚，不再疊加同義確認。已處理的人不因刷新或部署再次整合或寄送。
9. 新增唯讀資料體檢：列出未關聯來源、疑似重複有效名額、已答應未整合、信箱不一致、嘉賓出席與公開落差、住宿未跟進、舊作品待歸類及活動事實版本衝突。每項附原因、來源修訂及原記錄入口；讀取失敗顯示不可核對，不當作零。按原角色範圍取得最小資訊，不額外公開私人名單或自動修正。
10. 重用 `shared/organizer-progress.mjs` 與既有單人步驟產生「建議動作／原因／阻塞事項／依據修訂／操作入口」。平常只顯示下一步按鈕；有阻塞才補一句短原因及處理入口，依據修訂與歷史收在詳情。無權限者提供「交由审核人」等去向，避免只有無原因的灰色按鈕。建議由已保存事實決定，遇到未知回執先提供「核对结果」，不提供重建／盲重寄捷徑；清單讀取本身不觸發業務動作。此階段不接線上 AI 決策服務。
11. 在原型階段安排一次短操作觀察：一位實際同事完成找舊意向、記回覆、核對名額、交付私人連結；記錄入口尋找與狀態理解問題，修正後再做完整驗收。使用合成記錄或已授權業務範圍，不以操作觀察為由匯出全名單。

**主要檔案：**`src/lib/people-directory.mjs`、`src/lib/people-resolution.mjs`、`src/lib/person-workspace.mjs`、`src/lib/person-confirmation.mjs`、`src/scripts/person.mjs`、`src/scripts/registration-review.mjs`、`src/components/PersonConfirmation.astro`、`functions/people-operations/service.mjs`、`functions/person-workspace/`。

**P2 驗收：**不同來源同人只有一個有效名額；共用信箱不同人不誤合併；待審／拒絕／撤回不因整合改為核准；權限先於私有 I/O；來源失敗不顯示為零；未知回執沿用原操作；退出／換人／401 清除私有資料；歷史住宿與原問卷保留。唯讀體檢零業務寫入，每個建議能追溯原因與來源修訂，資料改變後不沿用過期建議。正式名單的實際核對依 [操作流程](02-staff-and-attendee-runbook.md) 執行，不由程式部署代做。

## P4 通知分型與行前提醒

本階段 `feat/redesign-p4` 從已發布 main `51ff34b` 接續；本地實作已有 1521 項完整回歸、最後公開瀏覽器及最終來源包校驗，公開／實際 FC 包內驗收均通過，PR CI 及實際發布仍待核對，見 [P4 紀錄](p4-release.md)。同一通知 journal 新增分型，既有政策版本、用途字串、部署環境值與舊待提交正文保持相容。

1. 沿用現有正式名額確認信及去重 journal；保留 `provider_accepted`、明確失敗與 `unknown`。寄信失敗不撤銷名額，unknown 不盲目重送。
2. 新增「申请已收到，待审核」回執通知型別，僅在新申請已持久化後處理。它不得占用正式確認信的通知身份，也不含群碼／Wallet 或已核准語意。失敗仍顯示已保存的申請與私人連結。
3. 新增一次行前提醒：管理者先預覽當時有效 confirmed 對象、訊息內容與數量，再明確啟動有界批次；先採既有後台受控派送模式，不直接建立排程服務或背景群發。訊息包含最新私人頁入口、報到與交通資訊，不附固定群碼。
4. 每種通知各自持久去重與記錄結果，明確定義事件／收件人主 ID／通知種類的身份。發送前重新核對資格、聯絡許可、地址、開關及時間預算；合併、刷新、重新導入與部署不觸發補寄。
5. 批次逐人顯示未嘗試、服務商接受、明確失敗及待核對，保留原操作回復。歷史已確認者由工作人員依實際通知紀錄選擇，禁止把「未看見信」當作未寄。
