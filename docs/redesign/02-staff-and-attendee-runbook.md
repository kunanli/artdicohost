## 活動行名冊與實際報到

1. 從活動行主辦方後台匯出本次活動的原始 `.xlsx`。在「人员与活动行」選「导入活动行」，先看預覽。檔案上限為 2 MiB、500 行，每次最多選 100 人。
2. 核對票號、姓名、有效票狀態及使用授權。共用信箱或同名的人先人工核對，再選沿用已核實的同一人或保留為不同人。只有實際選取且通過核對的資料才導入。換檔後以新檔的成功預覽為準。
3. 預覽依匯出資料顯示。工作簿的公式可能只提供匯出時的快取值，之後的取消或退票需回到活動行核對。匯入建立內部名冊或連結，名冊操作不發送網站確認信。
4. 保存回應不明時先按「核对原导入」。系統要求原檔時用同一份原始工作簿，再依畫面提示選「继续原导入」。已知原操作未寫入而畫面提供「重新预览」時，再核對新預覽；先前的選擇及確認須重做。
5. 活動當天請工作人員在活動行端掃描原電子票。查票、更正或退票直接在活動行辦理。既有的出席回覆、邀約歷史和已保存的安排仍可在本後台核對。

## 電子紀念卡申請、確認與寄送

1. 參與者先在活動行報名，然後填寫活動頁的紀念卡申請。準備活動行報名編號、姓名、Email 和微信號，並可填站點／社群、GGJ 參與經歷或 Jammer，以及學校／機構／團隊。在發卡頁可依姓名或活動行編號搜尋。[電子紀念卡申請](https://artdico.host/#wallet-card-application) · [後台發卡](https://api.artdico.host/admin/cards/)
2. 在活動行核對原票，回到卡片按「通过纪念卡申请」。保存已核實的卡面身分與補充資料，即可按「发送纪念卡」，也可先開啟 JPEG 預覽。選填電話會出現在 JPEG 與 Apple Wallet 詳情，Email 與微信號用於聯絡。
3. 收件人從郵件開啟私人頁，點「领取纪念卡」取得編號後下載 JPEG，也可在 iPhone Safari 直接點「加入 Apple Wallet」。後台的接收狀態來自郵件服務回執，實際收件與加入 Wallet 由真機驗證。
4. 需要重寄時直接按「重新发送纪念卡」。寄送結果不明時，原信可能已寄到。多次寄送測試使用「新增测试卡」和自己控制的信箱。
5. 「移除纪念卡」或「移除测试卡」會使該卡的線上領取連結失效。此前下載的 JPEG、已存入 Wallet 的卡片以及正式活動行報名均各自保留。要核對新版卡片，請從原來仍有效的私人入口重新領取。

## 人員歸檔、排班與未知結果

- 在個人工作頁核對原始來源、聯絡許可、實際回覆、公開身分與安排。同名或同信箱僅作線索。核實同一人再合併，原資料和歷史仍保留。已歸檔聯絡人退出邀約待辦與志工選單，仍有有效獨立報名者可沿用該報名。
- 已排期的場次和已確認的展位才計入有效安排。經嘉賓資料連到正式場次的講者或參與者也會計入。舊議程草稿保留供規劃，並可在編輯頁查閱；舊草稿上的班次會標記為待核對，可改連正式場次或取消班次後保留紀錄。同一合併身分只計一人，重疊班次不能同時安排。
- 志工儲存回應不明時，按「再次确认同一操作」，保留原表單和操作。如果另一位同事已修改同一筆，核對成功後會載入最新資料。匯出回應不明在原分頁核對，原檔仍可核對時會下載；若資料已更新，介面會確認原匯出記錄，請刷新後重新匯出。Excel 只在確有需要時勾選包含聯絡資料，匯出會有私有審計記錄。[志工操作手冊](../volunteer-operations.md)

## 歷史工作流程（P1–P6）

以下保留 2026-11-01（UTC+8）版手冊。網站申請、代登記、舊報名名額、參會私人頁、舊制郵件、群碼與入場票券操作均為往期紀錄。遇到舊連結時按上方的活動行與紀念卡流程處理。嘉賓、場次、展位與作品仍沿用保存、預覽、發布的步驟。

核心規則是一人一個工作入口、多份來源保留、一個有效參會名額。閱讀名單、部署程式或整合預覽不會替任何人答應出席、核准、合併、公開資料或寄信；這些由有權限的工作人員依實際業務操作。

日常只需「找人 → 核對下一步 → 保存」。需要時才展開來源／歷史；通知或公開內容先看預覽，再明確執行。結果未知先「核对结果」，不用重新填表、核准或重寄。

#### P1a 交接

P1a 已完成本地實作，正式發布狀態見 [交付紀錄](p1a-release.md)。發布後重新載入後台分頁，再依原有「保存 → 預覽 → 發布」操作：

- 作品新建與重新分類只有「学生作品」「独立游戏」。舊團隊作品顯示「待分类」，仍可修改其他內容並保存；核實後再選新分類，不必批次重填。
- 展位按需要使用「新增展位」，不再補齊空格。保留既有編號與關聯，核對位置衝突；取消記錄保留歷史。
- 保存仍只更新草稿；前台沿用已發布快照，須核對預覽後明確發布。程式上線不代為分類、安排展位或發布內容。

### 2 指派負責人與判讀狀態

依既有分工及帳號權限處理人員跟進、名額、通知、內容、微信群與住宿；需要接手時交由有權限的同事。不能由看得到某個按鈕推論具有其他資料權限。

#### 後台呈現規則

手冊保留完整處理依據，正式介面用短文字引導完成工作：

- 同一名單預設「待处理」，保留搜尋與「全部」；列表只突出姓名／機構、當前狀態與一個下一步。
- 點開同一人即可處理，不要求在多個工作區反覆找同一筆資料；原問卷、來源、歷史、完整安排與設定按需展開。
- 狀態要短且精確，例如「名额已确认」「寄送待核对」，不以籠統的「已完成」代替不同事實。
- 正常操作不常駐長說明；有阻塞就在按鈕旁提示一句，例如「信箱不同，请先核对」。沒有權限時提供「交由审核人」等去向。
- 普通保存不彈確認，成功後顯示「已保存」並留在同一人、同一位置。合併、撤回與發布保留必要的影響預覽。
- 原結果未知時突出「核对结果」，不讓同事為了繼續工作重新核准、重建報名或盲目重寄。

| 目前要處理的事 | 主要入口短文案示例 |
| --- | --- |
| 申請待審 | 审核 |
| 邀約待回覆 | 记录回复 |
| 已答應但待整合 | 确认名额 |
| 可寄正式確認信 | 发送确认信 |
| 上次結果未知 | 核对结果 |
| 名額已確認 | 查看凭证 |

短按鈕不改變原權限、保存及名額規則；「確認名額」仍先核對已有來源，並顯示實際確認／候補結果。以下四項事實繼續分別保存，畫面以緊湊摘要呈現，不各加一套操作流程。

| 核對事項 | 事實來源 | 不代替的事項 |
| --- | --- | --- |
| 本人出席回覆 | 實際 Email、微信等溝通後保存的回覆 | 原問卷預計到場、正式名額 |
| 審核及名額 | 正式名額服務的當前結果 | 內部審核意見、嘉賓身份 |
| 通知結果 | 保存的通知歷史 | 本人已收到、已讀、已入群 |
| 嘉賓發布 | 實際已發布版本與出席核對 | 綠色公開設定、保存草稿、確認信 |

一般參會、受邀嘉賓、講者可以是同一人。角色、場次、住宿與作品安排不額外增加個人名額；現行全場共同容量仍沿用既有政策，不因取消展位固定數量而改變。

### 3 路徑一 處理新網站申請（歷史）

1. 參與者填姓名、Email、身份及主動隱私同意；學校或機構、城市、微信選填。想演講者在同份申請補題目與簡介。
2. 實際保存後顯示「申请已收到，待审核」、編號與私人查詢連結。超時或結果未知時沿用原申請核對，不要求重填。
3. 審核人員從待審清單開啟單人資料，先核對是否已有舊意向或另一份網站申請。疑似重複先按第 4 節核對。
4. 核對完成後使用既有「审核通过并分配名额」或不通過操作。保存內部意見不會核准申請；滿額時以實際候補或衝突結果為準。
5. 核准回執成功後分別查看名額與通知結果。`confirmed` 才有正式確認信、有效群碼與就緒 Wallet；`waitlisted` 等待轉正。
6. 有演講提案者再安排主題、場次與職責。參會通過不等於演講獲安排，已有參會申請者補提案先聯絡主辦方，不重新建立報名。

P4 已發布獨立「申請已收到」Email 與行前提醒，證據見 [P4 發布紀錄](p4-release.md)。待審可有申請回執，但不占名額、不發正式確認信，也不提供群碼或 Wallet。

### 4 路徑二 整合舊意向與主辦方邀約（歷史）

#### 步驟一 只讀預覽資料

從現有私密名單查看來源、實際回覆、既有報名關聯與通知歷史，先整理待辦，不重新匯入原 Excel。舊文件記錄的問卷筆數是歷史紀錄，不能當作今日待處理數量。

| 目前狀況 | 下一步 | 參與者需要做什麼 |
| --- | --- | --- |
| 已關聯正式報名 | 沿用主記錄，核對最新狀態 | 不重填 |
| 疑似與網站申請重複 | 對照來源，人工確認是否同一人 | 必要時協助核對身份 |
| 已明確答應出席，尚未整合 | 依原來源整合，核對名額結果 | 收取本人私人連結 |
| 只有預計參加，尚未回覆 | 指派同事聯繫並記錄實際回覆 | 回覆是否前來 |
| 已婉拒或明確拒絕聯絡 | 停止邀約並保留處理歷史 | 不自動收到新邀約 |
| 聯絡許可不明 | 先核實許可與來源 | 不直接進入寄送批次 |
| 已確認名額但未通知 | 核對原通知後逐筆處理 | 從私人頁入群及保存票券 |

#### 步驟二 核對重複並保留主記錄

1. 使用既有「重复人员核对」檢查線索；同名、同信箱或共用聯絡方式均不自動合併。
2. 對照原問卷、網站申請、實際溝通及名額。核實同一人才選主資料，先預覽有效名額及關聯，再執行明確合併。
3. 保存後重新核對主報名、重複名額釋放與來源關聯。合併不自動核准待審者、不自動遞補他人或寄信，不復活已退出記錄。
4. 原問卷、同意、來源與通知歷史保留。誤合併沒有一鍵拆分；發現問題先停止該人的後續處理，保留來源，交資料負責人依[恢復流程](../maintenance-backup.md)核對。

#### 步驟三 確認出席並整合名額

有既有申請就沿用；只有舊意向者在核實答應後使用既有「确认出席并整合报名」。核對出席回覆已保存，再核對名額是確認、候補、待審或需審核人員處理，兩項結果分開。

工作人員整合保留原來源及代登記依據，不能代填成本人已在新網站勾選同意。原問卷的「預計到場」不升級成實際回覆，聯絡許可也不能由另一份記錄自動繼承。

#### 步驟四 補安排與交付私人連結

- 舊演講題目與簡介沿用，只補缺項；單純演講興趣不直接成為正式講者。
- 舊住宿需求留在原回答與跟進清單，指派住宿聯絡人核對，不因新版表單省略就改成不需要。
- 已安排的組織、作品、展位保留穩定關聯；移除申請入口不刪掉既有安排。
- 新的明確出席確認、核准或直接確認名額後，按既有設定處理一次確認信。歷史已確認者的補寄仍是有權限人員的逐筆動作，不能因整合部署整批重寄。
- 已確認者可從報名詳情取得私人參會連結，寄信或私下透過微信交給本人。沿用主報名連結，不要求再填表；人工交付與 Email 結果分開記錄。

### 5 工作人員每日處理順序（歷史）

P2 已發布：統一名單預設待處理，每人突出一個下一步，未知結果先核對；原問卷與歷史按需展開。以下為同事日常跟進順序，完成後核對實際回執，詳細證據見 [P2 紀錄](p2-release.md)。

| 順序 | 負責工作 | 完成判準 |
| --- | --- | --- |
| 1 | 通知或保存結果待核對 | 已核對原操作，未建立第二次不明操作 |
| 2 | 疑似重複 | 人工確認關係，主名額與來源一致 |
| 3 | 已答應但待整合、待審申請 | 實際名額結果可讀，與出席回覆分開 |
| 4 | 已確認待通知 | 原通知結果已核對，或私人連結已交本人 |
| 5 | 嘉賓及場次待更新 | 資料、角色與出席符合發布條件，公開版本已核對 |
| 6 | 群碼與住宿跟進 | 群碼有效；住宿需求有負責人及個別回覆 |

名額、寄信與發布各有獨立結果。介面只顯示可證明的狀態，不因出現 QR、下載票券或點連結就標示已入群、已加入 Wallet 或已到場。

### 6 參與者如何使用舊私人參會頁（歷史）

已發布的私人頁依序顯示狀態、活動時間地點、微信群、保存參會資訊。列印及個人邀請圖收在更多操作，並保留長姓名、缺圖、弱網及 Android 的替代方式，證據見 [P3 紀錄](p3-release.md)。

| 名額狀態 | 主要訊息與操作 |
| --- | --- |
| 待審核 | 已收到申請，保存查詢連結；不提供群碼、正式邀請或 Wallet |
| 候補 | 尚未確認名額，查看目前狀態，無需重填 |
| 已確認 | 查看何時何地、取得現行群碼、選擇加入 Wallet 或保存資訊 |
| 未通過 | 顯示結果與主辦方聯絡方式 |
| 已撤回 | 顯示取消，停止新票券下載及群碼取得 |
| 無法核對 | 提示保留原編號並重讀，清除前次個資與資格畫面 |

目前私人頁是查詢及下載入口，尚無本人線上確認出席、修改資料或取消功能。第一階段由主辦方依本人回覆操作；日後增加本人操作另列開發範圍。

連結遺失時，參與者聯絡 `support@artdico.co`；工作人員核對本人與主記錄後私下交付。編號本身不授權讀取私人資料，不要求另填新報名。

### 7 舊制 Email 的操作方式（歷史）

既有正式確認信從當前有效名額與聯絡許可判斷是否可寄。信中放私人參會頁連結；群碼從頁面取得，不把會過期的固定群碼附在 Email 裡。

| 後台結果 | 處理方式 |
| --- | --- |
| 尚未寄送 | 核對資格、信箱與許可後按現有寄送動作 |
| 服務商已接受 | 請本人檢查收件匣及垃圾郵件；不宣稱已送達或已讀 |
| 明確失敗 | 修正已查明原因，再依原重試機制處理 |
| 結果未知 | 核對原操作與服務商紀錄，不換操作編號盲目重寄 |
| 地址待核對 | 核對現用地址與原報名，不能只改聯絡卡就直接寄往另一地址 |
| 未收到或無可用信箱 | 保留名額，核對本人後私下交付參會連結 |

已發布的申請回執與行前提醒，與正式信分型顯示及去重，詳見 [P4 紀錄](p4-release.md)。提醒流程為「預覽 → 選人 → 寄送」，未知先核對原結果。舊名單不補發申請回執；提醒只由具權限同事明確操作，不由讀頁、部署或匯入觸發。

### 8 舊私人參會頁的微信群維護步驟（歷史）

1. 群維護人取得當前有效群碼，在群設定頁選圖片及真實到期時間，按保存並核對回執。
2. 設定上限為自目前起七天，不能靠改日期延長原微信 QR 的真實有效期。私人頁每次取得的圖片連結另有十分鐘期限。
3. 私人頁已提供「群碼待更新」「重新取得」與聯絡主辦方提示；沒有圖片時仍保留處理入口。參與者可依微信指引辨識或從相簿掃碼，真實入群結果另行確認。
4. 替換後核對新入口；網站舊圖網址失效不會收回別人已儲存的 QR 圖片。入群結果需本人或群管理員實際確認。
5. 參與者取消後，網站停止新群碼取得；已在群內者由群管理員依實際情況處理，系統不自動移出。

### 9 舊 Wallet 入場票券與現場報到（歷史）

依[最新 Wallet 設定紀錄](../apple-wallet-setup.md)，主辦方已完成簽章資料與 FC 可用性核對，剩 iPhone 真機驗收；保留現有設定，不重做開戶或輪替憑證。

1. 使用本人或明確授權、已確認名額的參會頁，在 iPhone Safari 實際開啟 Apple 添加畫面並加入，核對姓名、日期、時間、地點與條碼。
2. 微信內無法加入時提供 Safari 開啟指引；Android 或不使用 Wallet 者仍可使用私人頁及列印資訊。
3. 頁面只能顯示文件已準備，不能據下載成功宣稱已加入裝置。Wallet 為選用便利功能，不影響有效名額。
4. 現有卡片沒有 APNs 自動更新，也不會因撤回從手機消失；以當前線上資格核對為準。資訊更新後依私人頁指引重新下載，仍不能以下載代表已加入裝置。
5. 本階段現場依名單或編號由工作人員核對。現有票券掃碼只驗資格，沒有到場紀錄與重複入場判斷；QR 簽到另立階段。

### 10 嘉賓發布與住宿回覆

新發布的嘉賓區依已核實答應出席名單展示。內容人員核對穩定人員關聯、公開資料、角色及場次後保存，發布人員再核對全部待發布內容；一次發布會更新全部已保存內容，不只當前頁。取消出席時指派內容人員處理撤下及場次調整，核對新版前台，原資料與歷史保留。

舊公開快照若缺少新版出席證明，保留已公開嘉賓資料卡，不代表本人已答應或已有名額；明確空／錯誤證明與私人隔離不放寬。核對關聯後明確發布，才依新證明顯示確認名單，讀頁與部署不回寫舊快照。原相容修復見 [首頁紀錄](home-reference-release.md)，本輪字幕與實際素材修正的發布狀態見 [新紀錄](bubbles-logo-release.md)。

圓泡小字改用已公開的職稱；缺職稱才依序用 GGJ 身份、機構，沒有就留空，不填推測職稱或用「出席待确认」代替。長姓名與介紹可在展開內容完整閱讀。內容人員沿用原「保存 → 核對全部待發布內容 → 發布」，不用多填一份顯示狀態。

參與組織在前台只顯示已公開 Logo／名稱，按名稱可開啟已保存網站；不顯示「參展」「一般參與」等標籤，也不因此清除後台的參與安排。

替換 Logo 仍用原上傳與發布流程，不需手動選設計版本或填圖片摘要。顯示程式須依實際圖片摘要判斷是否可用設計版；後續換圖改用新上傳圖的有界框，不把白底方圖放大套用舊比例。上傳或保存都不等於已發布。
