# 工作人員與參與者操作步驟

更新日期：2026-11-01（UTC+8）。本手冊把舊意向名單、網站申請、邀約、正式名額及參會服務接成同一條工作流程。執行順序見[總覽](README.md)與[工程步驟](01-implementation-steps.md)。

核心規則是一人一個工作入口、多份來源保留、一個有效參會名額。閱讀名單、部署程式或整合預覽不會替任何人答應出席、核准、合併、公開資料或寄信；這些由有權限的工作人員依實際業務操作。

## 1 現有入口與本次改善

正式後台位於 `https://api.artdico.host`。現有入口可先繼續使用，P2 再將主要操作集中到單人工作頁。

| 工作 | 現有入口 | 本次改善 |
| --- | --- | --- |
| 找人與重複核對 | `/admin/contacts/` | 集中待回覆、待整合、疑似重複與待通知事項 |
| 查看同一人 | 從名單開啟 `/admin/person/` | 四項狀態與下一步集中呈現，減少往返 |
| 審核及名額 | `/admin/registrations/` | 主要動作依待審、候補、確認狀態顯示 |
| 確認信與 Wallet | `/admin/settings/delivery/` | 保留設定，集中異常處理及真機驗收結果 |
| 微信群 | `/admin/settings/group/` | 明確到期提醒與參與者端失效提示 |
| 嘉賓與發布 | `/admin/content/guests/`、`/admin/content/publish/` | 只展示確定出席者，取消後提示更新前台 |

舊文件中「沒有 Apple 憑證」「匯入或受托來源完全不能發確認信」等早期描述，以[10 月 30 日私人票券入口](../registration-workflow-simplification.md)、[10 月 31 日體檢](../health-2026-10-31-admin-wallet.md)及[人員整合](../unified-people-workspace.md)的較新行為為準。

## 2 指派負責人與判讀狀態

每天指定人員跟進、名額審核、通知處理、內容發布、微信群維護及住宿聯絡的負責人；一人可兼任。依既有帳號權限操作，不能由看得到某個按鈕推論具有其他資料權限。

### 後台呈現規則

手冊保留完整處理依據，正式介面用短文字引導完成工作：

- 同一名單預設「待处理」，保留搜尋與「全部」；列表只突出姓名／機構、當前狀態與一個下一步。
- 點開同一人即可處理，不要求在多個工作區反覆找同一筆資料；原問卷、來源、歷史、完整安排與設定按需展開。
- 狀態要短且精確，例如「名额已确认」「寄送待核对」，不以籠統的「已完成」代替不同事實。
- 正常操作不常駐長說明；有阻塞就在按鈕旁提示一句，例如「信箱不同，请先核对」。沒有權限時提供「交由审核人」等去向。
- 普通保存不彈確認，成功後顯示「已保存」並留在同一人、同一位置。合併、撤回與發布保留必要的影響預覽。
- 原結果未知時突出「核对结果」，不讓同事為了繼續工作重新核准、重建報名或盲目重寄。

| 目前要處理的事 | 主要入口短文案示例 |
| --- | --- |
| 申請待審 | 审核 |
| 邀約待回覆 | 记录回复 |
| 已答應但待整合 | 确认名额 |
| 可寄正式確認信 | 发送确认信 |
| 上次結果未知 | 核对结果 |
| 名額已確認 | 查看凭证 |

短按鈕不改變原權限、保存及名額規則；「確認名額」仍先核對已有來源，並顯示實際確認／候補結果。以下四項事實繼續分別保存，畫面以緊湊摘要呈現，不各加一套操作流程。

| 核對事項 | 事實來源 | 不代替的事項 |
| --- | --- | --- |
| 本人出席回覆 | 實際 Email、微信等溝通後保存的回覆 | 原問卷預計到場、正式名額 |
| 審核及名額 | 正式名額服務的當前結果 | 內部審核意見、嘉賓身份 |
| 通知結果 | 保存的通知歷史 | 本人已收到、已讀、已入群 |
| 嘉賓發布 | 實際已發布版本與出席核對 | 綠色公開設定、保存草稿、確認信 |

一般參會、受邀嘉賓、講者可以是同一人。角色、場次、住宿與作品安排不額外增加個人名額；現行全場共同容量仍沿用既有政策，不因取消展位固定數量而改變。

## 3 路徑一 處理新網站申請

1. 參與者填姓名、Email、身份及主動隱私同意；學校或機構、城市、微信選填。想演講者在同份申請補題目與簡介。
2. 實際保存後顯示「申请已收到，待审核」、編號與私人查詢連結。超時或結果未知時沿用原申請核對，不要求重填。
3. 審核人員從待審清單開啟單人資料，先核對是否已有舊意向或另一份網站申請。疑似重複先按第 4 節核對。
4. 核對完成後使用既有「审核通过并分配名额」或不通過操作。保存內部意見不會核准申請；滿額時以實際候補或衝突結果為準。
5. 核准回執成功後分別查看名額與通知結果。`confirmed` 才有正式確認信、有效群碼與就緒 Wallet；`waitlisted` 等待轉正。
6. 有演講提案者再安排主題、場次與職責。參會通過不等於演講獲安排，已有參會申請者補提案先聯絡主辦方，不重新建立報名。

P4 會新增獨立「申請已收到」Email 與行前提醒；它們尚未實作前，以頁面回執與現有正式確認通知為準，不把待審當作已寄正式邀請。

## 4 路徑二 整合舊意向與主辦方邀約

### 步驟一 只讀預覽目前資料

從現有私密名單查看來源、實際回覆、既有報名關聯與通知歷史，先整理待辦，不重新匯入原 Excel。舊文件記錄的問卷筆數是歷史紀錄，不能當作今日待處理數量。

| 目前狀況 | 下一步 | 參與者需要做什麼 |
| --- | --- | --- |
| 已關聯正式報名 | 沿用主記錄，核對最新狀態 | 不重填 |
| 疑似與網站申請重複 | 對照來源，人工確認是否同一人 | 必要時協助核對身份 |
| 已明確答應出席，尚未整合 | 依原來源整合，核對名額結果 | 收取本人私人連結 |
| 只有預計參加，尚未回覆 | 指派同事聯繫並記錄實際回覆 | 回覆是否前來 |
| 已婉拒或明確拒絕聯絡 | 停止邀約並保留處理歷史 | 不自動收到新邀約 |
| 聯絡許可不明 | 先核實許可與來源 | 不直接進入寄送批次 |
| 已確認名額但未通知 | 核對原通知後逐筆處理 | 從私人頁入群及保存票券 |

### 步驟二 核對重複並保留主記錄

1. 使用既有「重复人员核对」檢查線索；同名、同信箱或共用聯絡方式均不自動合併。
2. 對照原問卷、網站申請、實際溝通及名額。核實同一人才選主資料，先預覽有效名額及關聯，再執行明確合併。
3. 保存後重新核對主報名、重複名額釋放與來源關聯。合併不自動核准待審者、不自動遞補他人或寄信，不復活已退出記錄。
4. 原問卷、同意、來源與通知歷史保留。誤合併沒有一鍵拆分；發現問題先停止該人的後續處理，保留來源，交資料負責人依[恢復流程](../maintenance-backup.md)核對。

### 步驟三 確認出席並整合名額

有既有申請就沿用；只有舊意向者在核實答應後使用既有「确认出席并整合报名」。核對出席回覆已保存，再核對名額是確認、候補、待審或需審核人員處理，兩項結果分開。

工作人員整合保留原來源及代登記依據，不能代填成本人已在新網站勾選同意。原問卷的「預計到場」不升級成實際回覆，聯絡許可也不能由另一份記錄自動繼承。

### 步驟四 補安排與交付私人連結

- 舊演講題目與簡介沿用，只補缺項；單純演講興趣不直接成為正式講者。
- 舊住宿需求留在原回答與跟進清單，指派住宿聯絡人核對，不因新版表單省略就改成不需要。
- 已安排的組織、作品、展位保留穩定關聯；移除申請入口不刪掉既有安排。
- 新的明確出席確認、核准或直接確認名額後，按既有設定處理一次確認信。歷史已確認者的補寄仍是有權限人員的逐筆動作，不能因整合部署整批重寄。
- 已確認者可從報名詳情取得私人參會連結，寄信或私下透過微信交給本人。沿用主報名連結，不要求再填表；人工交付與 Email 結果分開記錄。

## 5 工作人員每日處理順序

P2 將以下待辦集中呈現；改版前可用現有清單、篩選與跟進日期完成。每筆設定一位跟進人和下一步，完成後核對實際回執。

| 順序 | 負責工作 | 完成判準 |
| --- | --- | --- |
| 1 | 通知或保存結果待核對 | 已核對原操作，未建立第二次不明操作 |
| 2 | 疑似重複 | 人工確認關係，主名額與來源一致 |
| 3 | 已答應但待整合、待審申請 | 實際名額結果可讀，與出席回覆分開 |
| 4 | 已確認待通知 | 原通知結果已核對，或私人連結已交本人 |
| 5 | 嘉賓及場次待更新 | 資料、角色與出席符合發布條件，公開版本已核對 |
| 6 | 群碼與住宿跟進 | 群碼有效；住宿需求有負責人及個別回覆 |

名額、寄信與發布各有獨立結果。介面只顯示可證明的狀態，不因出現 QR、下載票券或點連結就標示已入群、已加入 Wallet 或已到場。

## 6 參與者如何使用私人參會頁

私人頁依序顯示狀態、活動時間地點、微信群、保存參會資訊。P3 將列印及個人邀請圖收在更多操作，並保留長姓名、缺圖、弱網及 Android 的替代方式。

| 名額狀態 | 主要訊息與操作 |
| --- | --- |
| 待審核 | 已收到申請，保存查詢連結；不提供群碼、正式邀請或 Wallet |
| 候補 | 尚未確認名額，查看目前狀態，無需重填 |
| 已確認 | 查看何時何地、取得現行群碼、選擇加入 Wallet 或保存資訊 |
| 未通過 | 顯示結果與主辦方聯絡方式 |
| 已撤回 | 顯示取消，停止新票券下載及群碼取得 |
| 無法核對 | 提示保留原編號並重讀，清除前次個資與資格畫面 |

目前私人頁是查詢及下載入口，尚無本人線上確認出席、修改資料或取消功能。第一階段由主辦方依本人回覆操作；日後增加本人操作另列開發範圍。

連結遺失時，參與者聯絡 `support@artdico.co`；工作人員核對本人與主記錄後私下交付。編號本身不授權讀取私人資料，不要求另填新報名。

## 7 Email 的操作方式

既有正式確認信從當前有效名額與聯絡許可判斷是否可寄。信中放私人參會頁連結；群碼從頁面取得，不把會過期的固定群碼附在 Email 裡。

| 後台結果 | 處理方式 |
| --- | --- |
| 尚未寄送 | 核對資格、信箱與許可後按現有寄送動作 |
| 服務商已接受 | 請本人檢查收件匣及垃圾郵件；不宣稱已送達或已讀 |
| 明確失敗 | 修正已查明原因，再依原重試機制處理 |
| 結果未知 | 核對原操作與服務商紀錄，不換操作編號盲目重寄 |
| 地址待核對 | 核對現用地址與原報名，不能只改聯絡卡就直接寄往另一地址 |
| 未收到或無可用信箱 | 保留名額，核對本人後私下交付參會連結 |

P4 新增「申請已收到」與行前提醒時，必須各有獨立通知身份、收件範圍及去重紀錄。舊名單不自動補發申請回執；提醒也不由閱讀頁面、部署或匯入資料觸發。

## 8 微信群維護步驟

1. 群維護人取得當前有效群碼，在群設定頁選圖片及真實到期時間，按保存並核對回執。
2. 設定上限為自目前起七天，不能靠改日期延長原微信 QR 的真實有效期。私人頁每次取得的圖片連結另有十分鐘期限。
3. P3 補齊「群碼待更新」「重新取得」與聯絡主辦方提示，避免沒有圖片時整區消失。參與者可長按辨識，或儲存圖片後從微信相簿掃碼。
4. 替換後核對新入口；網站舊圖網址失效不會收回別人已儲存的 QR 圖片。入群結果需本人或群管理員實際確認。
5. 參與者取消後，網站停止新群碼取得；已在群內者由群管理員依實際情況處理，系統不自動移出。

## 9 Wallet 與現場報到

依[最新 Wallet 設定紀錄](../apple-wallet-setup.md)，主辦方已完成簽章資料與 FC 可用性核對，剩 iPhone 真機驗收；保留現有設定，不重做開戶或輪替憑證。

1. 使用本人或明確授權、已確認名額的參會頁，在 iPhone Safari 實際開啟 Apple 添加畫面並加入，核對姓名、日期、時間、地點與條碼。
2. 微信內無法加入時提供 Safari 開啟指引；Android 或不使用 Wallet 者仍可使用私人頁及列印資訊。
3. 頁面只能顯示文件已準備，不能據下載成功宣稱已加入裝置。Wallet 為選用便利功能，不影響有效名額。
4. 現有卡片沒有 APNs 自動更新，也不會因撤回從手機消失；以當前線上資格核對為準。資訊更新後需要重新下載的指引納入 P3。
5. 本階段現場依名單或編號由工作人員核對。現有票券掃碼只驗資格，沒有到場紀錄與重複入場判斷；QR 簽到另立階段。

## 10 嘉賓發布與住宿回覆

新版嘉賓區只展示已核實答應出席者。內容人員核對穩定人員關聯、公開資料、角色及場次後保存，發布人員再核對全部待發布內容；一次發布會更新全部已保存內容，不只當前頁。取消出席時指派內容人員處理撤下及場次調整，核對新版前台，原資料與歷史保留。

第一次切換新版前先核對發布預覽：舊公開快照若缺少新的出席證明，嘉賓區會顯示待公布，不能靠舊資料確認欄位推定到場。工作人員核對關聯並明確發布後才出現確定出席名單，其他公開區塊不因缺此證明失效。

網站住宿 Q&A 採簡體中文：

> **外地来宾有住宿支持吗？**
>
> 本次活动提供少量外地来宾住宿支持。有需要的朋友，欢迎提前通过 support@artdico.co 联系主办方了解安排；名额有限，住宿安排将另行确认。

P3 與 P5 提供信箱連結及複製方式，與公開聯絡設定保持一致。住宿聯絡人收到來信後先查既有人員，沿用跟進紀錄；住宿安排由主辦方個別確認，不改參會名額或自動承諾房間。

## 11 執行及交付檢查

- [ ] P2 以合成人員走完新申請、舊意向、重複關聯、候補及明確拒絕情境，核對來源與單一名額。
- [ ] P3 驗證私人頁、群碼過期、連結遺失處理、iPhone 與 Android 指引；真機結果單獨記錄。
- [ ] P4 核對通知種類、歷史去重、明確失敗與未知結果；開發測試使用替身服務，不向真實名單實寄。
- [ ] P5 核對確定出席嘉賓、兩類作品、已安排展位及所有移除的申請入口。
- [ ] P6 核對首頁、私人頁、新 Email 與新票券的活動資料一致；舊 Email 和已存票券不自動改寫。
- [ ] 正式操作名單時先做只讀預覽，再逐筆或小批核對，保留原始資料、來源、通知與處理歷史。

遇到保存結果不明，保留原內容及同一操作核對；不能用新名額、新人員或清除通知歷史來繞過問題。備份、回退與刪除沿用[維護流程](../maintenance-backup.md)及[部署步驟](../08-deployment.md)。
