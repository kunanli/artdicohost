# ARTDiCO HOST 改版驗收與發布步驟

這份清單與 [開發步驟](01-implementation-steps.md) 配合使用。每個階段以相應合成情境通過為完成條件；正式發布另核對準確提交與實際產物。未勾選的項目是後續工作，文件交付不代表產品已上線。

## 當前 P1a 紀錄

兩類作品、舊分類相容與動態展位已完成本地實作，全套 Node 測試、來源／Astro 檢查、本地構建、Skill 回歸、審計、聚焦瀏覽器及本地來源包核驗已通過。[P1a 實作與發布紀錄](p1a-release.md) 記錄準確結果；PR CI 準確候選產物及實際發布證據待完成。下方文檔／Skill 準備結果為較早基準，不代表本階段或 P1b 以後已完成。

## 步驟一 固定開發與驗收來源

1. 開工前核對 `git status`、分支、遠端 main 與最近實際發布結果。保存使用者改動，建立該階段獨立分支，不使用歷史接續文件中的舊 SHA 覆蓋新程式。
2. 本輪文檔基準為 `d583e4de9ae1676822c6ea6da984211099f73dd3`；執行當日若 main 前進，以新基準重新核對相容與部署包。
3. 沿用 Node `24.19.0`、pnpm `11.25.0` 與鎖檔。依賴未變時不為本輪重做版本升級；未來更換執行期另核對支援狀態與現有封裝契約。
4. 先用合成來源、合成姓名及 `example.invalid` 信箱驗證。測試 provider、內存／隔離物件與瀏覽器攔截不可連到真實收件人、群碼或名單。
5. 不以 localhost 直接讀正式 API 作預覽；現有公開 Origin 有固定限制。使用合成本地 API／受測試控制的攔截，或明確配置的隔離預覽，不放寬正式 CORS 解決預覽問題。

## 步驟二 依階段跑必要檢查

在倉庫根目錄執行，先確認目前階段的依賴已安裝。產品開發的基本命令為：

```sh
pnpm install --frozen-lockfile
pnpm check:source
pnpm check
pnpm test
PUBLIC_API_BASE=https://api.artdico.host PUBLIC_CONTENT_API_ORIGIN=https://api.artdico.host pnpm build
pnpm audit --audit-level=moderate
```

這些命令不代表對正式申請做測試；完整 CI 還有準確來源包、離線 smoke 及發布後核驗。定向測試先處理本階段行為，通過後完成既有必要全套檢查；沒有新變更或未解疑慮時不反覆重跑。

僅文件變更驗證 Markdown 連結、決策一致性、差異及敏感內容即可，不以未執行的完整構建宣稱新版功能已通過。瀏覽器測試沿用 [現有環境與命令](../../tests/browser/README.md)。

新增的 [契約檢查 Skill](../../.agents/skills/artdico-contract-check/SKILL.md) 與 [旅程驗收 Skill](../../.agents/skills/artdico-journey-check/SKILL.md) 提供固定案例的本地入口；先閱讀 SKILL.md 的範圍再執行。runner 通過只代表選定合成案例通過，仍需補本輪新規則、準確構建、真機及發布證據。

| A14 | 首頁、私人頁、新郵件與新 Wallet 日期地點 | 使用同一核實活動版本；已寄信及已存票券的舊資料不假稱會自動更新 |
| A15 | 無群碼、過期、圖片連結十分鐘後失效、換碼 | 顯示待更新／重新取得／聯絡方式；從私人頁取現行碼，未確認與取消者不能新取得；不假報已入群 |
| A16 | Wallet 未就緒、有效簽章、撤回、舊卡掃碼 | 正確顯示可用性，撤回拒絕新下載及有效核驗；已存卡不假稱自動刪除，驗票不寫成已完成簽到 |

| A18 | 新申請回執、行前提醒、歷史匯入／一般讀取 | 新通知種類去重獨立；讀取、部署、匯入與合併不觸發歷史補寄；供應商失敗不回退申請 |
| A19 | 報名關閉／API 無法核對，且 FAQ 重新發布 | 按鈕與聊天 Q&A 保持同一實際狀態，隱私／聯絡更新可見；動畫不掩蓋故障 |
| A20 | 一般／邀約／審核／內容／發布角色權限 | API 先做權限與來源校驗；僅被授權的操作可讀寫相應資料，公開畫面不為方便查詢而讀私人名單 |
| A21 | 唯讀資料體檢、缺少來源或缺少權限 | 異常有原因、來源修訂與原記錄入口；不自動改資料，不跨權限讀取，來源不可用不顯示為零 |
| A22 | 下一步建議、資料更新與未知回執 | 建議可解釋且來自已保存事實；過期建議先重新核對，unknown 優先核對原操作，讀取不觸發合併／核准／寄信 |

## 步驟四 驗證版型與實機

使用 320、390、1440px 檢查基準版型，並完成實際微信與 iPhone 驗收；桌面模擬不替代真機。

- [ ] 首頁長姓名、缺照片、零／一／多作品、大量組織及展位無橫向溢出，單件作品不顯示無效切換。
- [ ] 手機嘉賓卡可點擊／關閉；桌面滑鼠移入卡片不誤收起，鍵盤可操作並正確返回焦點。
- [ ] 輪播、篩選與更新內容後維持目前作品或合理回退；撤下項目不留下舊卡片。
- [ ] A／B／C 切換有文字及選中狀態；嘉賓／作品跳到場次會切對區域及時段，保留既有錨點。
- [ ] reduced motion、JavaScript／圖片失敗時核心資訊仍可讀；背景或星球轉動不帶動正文倒轉。
- [ ] 微信內可保存私人連結、複製信箱、長按或從相簿辨識群碼，失效時可重新取得。
- [ ] iPhone Safari 實際下載 Apple 簽章票券、顯示添加介面並加入；核對姓名、日期地點、版型及線上資格掃碼。只記錄測試結果，不留公開私人連結或憑證。
- [ ] 微信內 Wallet 開啟限制有 Safari 指引；Android／不使用 Wallet 者可從私人頁取得完整參會資訊。
- [ ] 私人確認頁的列印不含 capability 網址與群碼，仍清楚標示讀取當時狀態。
- [ ] 活動分享圖、標題、描述與核實內容一致；微信分享以實機結果記錄。首頁索引未定案前保留現況，私人頁持續禁止索引。

實機使用本人或明確授權且符合資格的記錄。既有 Apple 簽章資料保留，不為驗收重新申請帳號或輪替密鑰。收件實測依實際業務授權範圍執行，不拿歷史名單作群發測試。

## 步驟五 檢查素材與部署包

1. [公開產物選取](../../scripts/prepare-oss-site.mjs) 只發布固定路由及引用到的 `_astro/` 資源；將優化衍生圖放入 `src/assets`，不要假設 `public/assets/` 或原始素材目錄會自動發布。
2. [FC 隔離建置](../../scripts/cloud-content-package.mjs) 只複製既定來源，仍執行完整 Astro build。首頁不要直接跨目錄 import FrontEnd_Resource，否則 FC 建置也可能失敗。
3. 新首頁字型／背景限定首頁樣式，避免進入共用 Layout 的後台依賴。FC 資源白名單主要為 CSS／JS／WOFF；共享背景圖引用須檢查產物支援，不能只看本機可顯示。
4. Noto 有既有 OFL 依據，製作 WOFF2 子集並保留授權及系統字型備援；子集需能處理未來新增姓名。MiSans 附屬檔不可當字型本體。
5. 原始照片、Logo、作品圖經既有裁切／壓縮流程，符合 512 KiB 及 2048×2048 服務端上限；Logo 保留自然比例，原材料網址不直接變公開連結。
6. 沿用既有包上限：128 個檔案、40 個後台靜態資源、單資源 2 MiB、靜態合計 8 MiB，以及 [FC JSON 請求 48,000,000 bytes 與其 ZIP 推導上限](../../scripts/fc-upload-limits.mjs)。實際 bytes 由本輪準確產物重新核對，不沿用舊體檢餘額。
7. 新服務／shared 檔案若進執行依賴，更新準確來源閉包及驗證，不直接放寬數量或大小限制。先調整合理 chunk／首頁依賴隔離，再處理確有必要的變更。
8. 使用現有 [check.yml](../../.github/workflows/check.yml) 的候選產物、離線 smoke、公開產物 manifest 與逐檔 hash 核對。只有準確提交的檢查通過，才沿用其候選包發布。

本輪預期不新增雲資源、DNS、IAM 或秘密。若新郵件數量超出供應商配額，記錄受影響範圍並維持頁面可用，不自動購買升級。

## 步驟六 發布與現場準備

1. 記錄本階段 PR、head／merge SHA、契約影響、測試、產物大小及相容回退版本；PR 審查與檢查通過後按現有流程合併。
2. main 發布核對實際 FC 與 OSS job、準確來源回執、匿名 HTTPS／CORS 及公開物件內容；失敗繼續診斷或回退，不能只憑綠色 PR 宣稱上線。
3. 前次純文檔交付不觸發部署；各階段產品交付使用既有 [自動部署](../automatic-deployment.md)、[FC 自動部署](../automatic-fc-deployment.md) 與現行 workflow。API、公開投影與前端須同一候選版本交付，完成後提醒操作人員重新載入分頁，不照抄早期尚未啟用服務的紀錄。P1a 已發布證據見 [P1a 紀錄](p1a-release.md)，當前 P1b 狀態見 [P1b 紀錄](p1b-release.md)。
4. 技術發布後，工作人員依 [操作手冊](02-staff-and-attendee-runbook.md) 檢查名單整合預覽、素材 ID、嘉賓與場次，再明確執行相應業務操作。發布全部已保存內容的範圍需在預覽清楚呈現，避免順便發布無關草稿。
5. 活動前指定群碼維護與通知異常負責人，確認查名單／編號的現場方式。QR 到場簽到尚未列入本輪，不以 Wallet 有條碼就當作已有簽到工具。
6. 活動後資料保留、更正、撤回、刪除及備份到期沿用既有受控流程；舊意向與關聯來源一併納入。開發不宣稱已自動清除所有副本。

## 步驟七 回退與資料修復

1. 先判斷故障屬於程式、發布內容、通知或業務資料；不要以回滾程式覆蓋最新名單。
2. 通知有風險時先暫停相應新發送，保留原通知 journal 與 unknown 狀態。群碼／Wallet 故障不能撤銷已確認名額。
3. 準備修改正式資料前，依 [加密備份與隔離恢復](../maintenance-backup.md) 保存受限備份並驗證，密鑰另存；操作來源與摘要不放入公開工件。
4. 程式回退僅使用認得新欄位、既有 personGroups／v3 與通知身份的相容版本。不得回到只接受 15 個位置或不認得已寫新欄位的舊寫入者。
5. 錯誤資料合併先核對全部來源與操作歷史；現有流程沒有一鍵拆分，不自動復活被撤回的重複報名。
6. 業務恢復先寫隔離位置、驗證來源／撤回及刪除要求，再按既有流程切換；不直接以歷史快照覆蓋現行正式資料，也不清通知預留來繞過去重。
