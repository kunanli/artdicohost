## 本階段範圍

| 通知 | 時機與邊界 |
| --- | --- |
| 申請已收到 `application_received` | 僅對可信新建、已持久化的公開申請嘗試回執；明確表示待審，不含群碼、Wallet 或已核准語意。通知失敗仍保留申請及私人查詢入口 |
| 正式確認 `registration`／`promotion` | 沿用現有資格、去重、未知結果及正式名額通知，不被申請回執或提醒抑制 |
| 行前提醒 `pre_event_reminder` | 具既有通知權限的同事先看固定內容與有效 confirmed 對象，再選取及明確寄送，每批最多一百人。實際發送前再次核對身份、名額、許可、信箱、通知開關、活動事實與期限 |

三種用途按通知種類分別去重，保留已保存的主身份與來源關聯。讀頁、重放、匯入、整合及部署不補寄歷史名單；同信箱不代表同人，預留／已接受／未知結果不重新寄送。

私人頁保留原 `email` 代表正式信的意義，以可選 `notifications` 分型呈現其他通知；舊回應缺少新欄位仍可讀。服務商接受只代表服務商接收請求，不表示送達或已讀。

## 工作人員操作

**預覽 → 選人 → 寄送。** 每筆顯示未嘗試、服務商已接受、明確失敗或待核對；未知時主要動作為核對原結果，不建立另一筆重寄。未嘗試者才另行選取，來源不可讀便顯示待核對。

提醒由明確操作啟動，不建立排程。寄信結果不撤銷已保存的申請、回覆或名額；處理失敗與核對原結果時保留原操作及輸入。

## 設定與相容

沿用同一通知 journal、既有前綴及 EmailJS 中性模板，仍只使用 `to_name,to_email,event_title,event_date,event_time,event_venue,reference_code,invitation_text` 八個欄位。不新增服務、依賴、憑據或執行檔案；不實寄或操作正式名單。

`approvedRegistrationPolicy` 的版本、用途字串及部署環境值維持不變。就近說明必要通知用途與最小服務商欄位，不改寫原始同意，也不使舊待提交正文／鍵失效。

新通知種類進入原 journal 後，備份與隔離恢復必須保留並能解析它們。回退只能用認得新種類及既有未知結果保護的相容寫入者；不能以舊程式、舊快照或清空通知紀錄來回退。具體流程沿用 [備份及隔離恢復](../maintenance-backup.md)，本階段同步核對其契約。

既有 2000 份通知、4000 筆稽核、1 MiB journal 及候選包界限保持不變。
