# 工作人员账号管理

## 本轮协作账号与入口

现有管理员登录 [用户管理](https://api.artdico.host/admin/settings/#staff-accounts-title)，分别建立 **zhouyufei**、**wangying**：

1. 按「准备 zhouyufei」；预填姓名、四项业务角色并生成独立初始密码，尚未创建账号。邮箱选填，不猜测地址。
2. 保持「启用此账号」，按「保存工作人员账号」。
3. 看到「工作人员账号已保存并核对权限」及清单的已启用记录后，从「本页已确认保存的登录资料」显示／复制密码，私下交付本人。
4. 同样建立 wangying。密码只留在当前页面，离开或登出会清除，不进入本机草稿、链接、仓库或日志。

当前开发环境没有现有管理员会话，因此两个正式账号尚未实际创建。不能把快捷预填、合成浏览器测试或部署成功称为业务账号已建立。

| 权限组合 | 能做什么 |
| --- | --- |
| 协作者：editor、publisher、outreach、reviewer 四项全部勾选 | 内容编辑与发布、人员邀约与安排、报名审核／名额、Excel 导出、通知设置与群码 |
| superadmin | 上述能力，以及新增／修改／停用账号、备份与隔离恢复 |
| 单项或不完整组合 | 保留各项原有职责；不会因少数角色自动取得完整营运权限 |

账号的「启用」取消勾选并保存即为停用，既有会话立即失效；人员内容与操作历史保留。受保护的 owner 不能在页面覆盖。两位协作者看不到账号或恢复工具，前端也不请求这些受限接口，服务端仍逐次验证权限。

填写的非秘密字段可暂存本机，恢复后须重新输入密码；后台版本不同只能查看原填写。有效保存必须核对修订号、唯一目标 ID、用户名、角色和启用状态。结果未知不自动重复创建；重新读取目录也不能证明密码已保存，须核对现有稳定 ID，必要时明确重设密码并取得新回执。

受控配置中的 owner 保留为恢复账号，用户名／密码摘要由 GitHub 配置流程管理，不能从后台覆盖。其他工作人员由 superadmin 在 `/api/admin/users` 创建、修改角色、重设密码或停用，最多合计 20 位；邮箱必须是明确填写的 `@artdico.co` 身份，域名本身不授予任何权限。

新增账号目录使用独立私有日志 `cms/v1/users`，只保存 scrypt 摘要和最小审计；接口不返回摘要或明文密码。写入采用预期修订号，冲突须重载；未知写入结果不自动重送。owner 不会因为目录失败回退到一个绕过验证的缓存，储存故障时登录与会话核验保持失败。

`createCloudAuth` 可使用明确的 `usersProvider`。每次登录和会话验证读取当前目录，账号停用、密码摘要或角色变化通过凭据指纹立即使既有会话失效，不需等候八小时到期。角色独立：editor 编辑公开稿件、publisher 发布、outreach 私密意向名单、reviewer 报名审核、superadmin 账号与完整受控运维；不会自动把编辑角色升级为报名读取权限。

管理 API 的 GET／POST 均需要已登录 superadmin，POST 另需准确 Origin 与 CSRF。模块单独构造默认关闭，现有云端 runtime 已明确装配；本轮权限及界面变更的准确发布状态以[接续台账](session-recovery.md)为准。

验证：`node --test tests/cloud-users.test.mjs tests/cloud-auth.test.mjs tests/registration-admin.test.mjs` 共 28 项通过，覆盖目录重建、并发冲突、保护 owner、重复身份拒绝、停用和角色变更跨实例撤销、储存失败及最小响应。
