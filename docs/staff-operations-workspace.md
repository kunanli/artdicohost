# 人员串联、步骤指引与设置中心

本轮保存与公开操作以[统一保存](admin-save-workflow.md)、[默认公开](default-public-visibility.md)和[本轮验收／发布记录](admin-save-visibility-release-2026-10-22.md)为准；旧版先应用再保存、保存后关闭编辑及公开前确认／授权门槛不再作为日常步骤。个人工作页只读整合既有记录，不自动转换报名、发送邮件或发布人物。

历史发布证据：[PR #34](https://github.com/kunanli/artdicohost/pull/34)／main `ddf7a2ea0b9c81d9222aefbef3e5155d7432b8a4`，877 项检查、实际私有 OSS、300 人政策及 26/26 HTTPS 对象通过。[完整历史证据](staff-operations-release-2026-10-21.md)、[接续台账](session-recovery.md)。这些数字不代替本轮准确来源和正式验收。

## 怎样安排这份意向名单

从「人员与邀约」打开某人的「个人工作页」。同一页集中显示原有联络资料、负责同事、下次跟进、实际回复、报名与名额、场次／展位及邀请／确认信记录。跨页只带内部 ID；不会按姓名、邮箱或组织名称自动合并。

| 步骤 | 要做的事 | 依据与后续入口 |
| --- | --- | --- |
| 1. 核对意向 | 核对姓名、机构与联络同意，保留原问卷 | 原始来源和当前资料分别保存；进入「编辑资料」修正当前联络资料 |
| 2. 联络与回复 | 指定负责同事、下次跟进并记录实际沟通结果 | 进入「详情与安排」记录跟进；需要邀请时进入对应邀请流程 |
| 3. 确定参与身份 | 按实际谈妥的内容选择嘉宾、讲者、主持、组织者、展位或一般参会等职责 | 同一人可有多个全活动职责；角色改变不重建人员／报名，不代替本人回复 |
| 4. 安排场次／展位 | 给有对应职责者分配场次、逐场职责及展位 | 一般参会者不必获得场次或展位；取消／缺失引用须重新核对，不能当有效安排 |
| 5. 核对公开资料 | 核对头像、职称、介绍、公开职责与授权，再保存及发布 | 嘉宾资料使用明确人员关联重新打开；存在资料不等于已经公开 |

步骤是当前已保存事实的导引，不是自动执行的工作流。资料受限或读取失败时显示「无权查看／暂不可用／待核对」，不能当作已完成。名额、审核、实际出席回复与人物公开授权分别维护。

## 数据怎样串联

- 联系人有稳定 `contactId`，原问卷与后续跟进保留。同一来源再次导入不覆盖当前跟进。
- 工作人员明确代登记后，以已保存的转换记录及报名 provenance 连接 `registrationId`。没有明确关联时保持未关联，不通过姓名／邮箱猜测。报名详情同样可打开个人工作页。
- 人员的 `sessionIds`、`sessionRoles` 与 `boothIds` 指向已保存内容的稳定 ID；内容草稿和人员日志有各自修订号，页面不声称跨日志原子一致。
- 嘉宾资料通过明确的来源人员 ID 关联，不建立同名副本。内部职责、公开职责、本人出席回复与发布状态分别核对。
- 公开快照不含私人联系人 ID。若草稿中的关联嘉宾已被移除，而旧公开快照仍有无法归属的嘉宾，个人页会提示发布状态待核对，不按名字反查或声称此人已停止公开。
- 邀请图生成、工作人员实际发出、服务商接受、实际回复与确认信结果按各自来源显示。服务商接受不证明送达；下载 PNG 不证明已发出。未知发送结果先核对，不能盲重送。

参与组织名录仍是独立内容资料；组织名称相同不自动绑定或占用展位。某个人有展位安排也不自动发布整间组织。十五个展位、组织图片／链接和公开授权仍在各自编辑器明确维护。

## 权限与只读接口

个人页入口为 `/admin/person/#contact=<内部ID>` 或 `/admin/person/#registration=<内部ID>`，fragment 不含姓名、邮箱或私人确认链接。

| 权限 | 可以查看 |
| --- | --- |
| outreach | 联系人、跟进、最小场次／展位、邀请与已关联的最小名额状态；没有完整报名审核或确认信历史 |
| reviewer | 报名、审核、名额与最小确认信历史；没有名单原始意向、私人跟进或工作人员邀请 |
| superadmin／组合权限 | 按实际授予的范围组合呈现；editor 单独不能读取私人人员资料 |

`GET /api/admin/people/contacts/:id` 与 `GET /api/admin/people/registrations/:id` 均在读取来源前鉴权；界面不能通过隐藏元素代替后端权限。接口不返回完整原始问卷、来源摘要、EmailJS 密钥、私人确认 capability 或邮件正文。历史列表有明确上限、总数及截断说明；不可用与没有记录区分显示。

## 设置与通知

独立 `/admin/settings/` 集中确认邮件／Wallet、微信群码与管理工具。自动报名确认与工作人员邀请分别配置、分别记录。读取、刷新及登录不发送邮件，普通网页不收集或回传寄件密钥／签章私钥。

用户已回报 EmailJS 测试收件正常并完成受控 key 设置，确认模板为 `template_89mgpj9`。本轮不替用户重置开关或凭证，也不把该回报称为新的独立实寄验收。Wallet 等 Apple Developer enrollment、真实 Pass Type ID／证书与 iPhone 验收，参见[邮件设置](emailjs-registration-setup.md)及[Wallet 设置](apple-wallet-setup.md)。

## 接续、验证与回退

展位与内容表单修改后直接按附近「保存」，以「未保存 → 保存中… → 已保存」和本次精确云端回执核对结果；成功后保留编辑对象，继续修改同一对象。失败／冲突保留填写，不以自动刷新覆盖，也不把总览刷新失败误写为保存失败。旧版「应用到本页 → 保存到云端」两步指引仅属历史。未发送到服务器且已刷新清除、没有可恢复本机草稿的输入，开发端没有云端原件，不能承诺找回。

日常操作：列表公开开关直接保存，编辑窗开关随本表单「保存」提交，再明确「发布到前台」更新全部已保存活动内容；有未保存填写时先「保存并发布」。开关不改实际回复、名额或授权事实；相关资料／照片变更仍重核该份授权，不关闭公开开关或阻挡发布。常规本机暂存不当作云端保存结果，已载入草稿固定浮窗移除；恢复／冲突／未知提交时才显示工具。关闭表单、退出与刷新均保护未保存内容。

若显示保存结果未确认，保留本页并点击核对保存结果。内容与较新云端版本完全一致时确认保存；明确读回仍是原版本时，才提供「重试同一份保存」，使用原内容与原修订号，后续编辑不混入重试。云端已有不同更新时显示冲突，不自动覆盖或合并。保存反馈留在表单附近，不使用固定浮窗；320／390px 最后一列操作仍可点击。

当前只是新增页面与只读投影，沿用已有 Astro、FC、私有 OSS 与写入审计；零新增云服务、IAM、DNS 或收费依赖。所有设置修改仍使用既有鉴权／CSRF、修订与未知结果处理，保留未保存资料保护及登出／换账号隔离。

测试只使用合成资料：验证稳定关联、角色在读取前拒绝、来源不可用、历史语义、无自动发送／写入、换账号与晚到回应，以及手机操作。完整检查、来源候选 ZIP、准确 PR／main CI、十阶段私有 OSS、300 人政策与公开 HTTPS 资源分别取证。

部署前验证包含实际 run ID 的完整环境大小；若超过既有 4096 bytes 上限，在暂停服务之前失败，不截断现有邮件变量。候选源码文件上限 128，静态文件 40 与十阶段／1000 次请求／90 秒验收限制保持。

回退先核对最新已验证 main 与来源包，保留全部业务日志、通知预留和用户受控环境；只回退兼容现有 schema 的代码，不用旧数据快照覆盖后续报名或沟通。生产是否完成上线只以接续台账的实际运行证据为准。
