# 人员、报名与角色名单

2026-10-31，接续已发布的 HTTP 400 修复 main `fa2df37`。用户选择参展商以公司／团队列出，并要求确认名额后寄确认信，收件人从私人确认页添加 Wallet。发布提交、CI 与实际 HTTPS 验收结果见 [PR #47](https://github.com/kunanli/artdicohost/pull/47)；合成验证不代表真实收件或 iPhone 实机通过。

## 同一工作区

「人员与报名」为共同导航入口：统一名单、待分流、一般参会者、报名审核、参展商、讲者、受邀嘉宾。完整的邀约、导入、转换、批次及导出工具仍保留，在日常名单后收合；旧审核、邀约深链及个人工作页继续可用。

统一名单只按保存的 sourceContactId／转换关系连接联系人与报名，既有明确关系只占一行。自行公开报名、工作人员直接登记、没有联系人关系的人物资料分别保持来源；姓名／邮箱相同只作为疑似重复线索，未经工作人员确认不合并。明确合并后，同一人沿用一个主报名，不复制人员或新增名额。每行集中显示姓名／机构、当前角色、邀约／跟进和正式报名状态，再提供管理入口。

## 重复人员与意向分流

当前阶段依据用户确认的「主要是重复人员资料」，提供受保护的重复核对流程，不会在部署或读取页面时自动清理真实名单。

1. 打开「重复人员核对」，点击「检查疑似重复人员」。标准化邮箱、微信、电话或姓名加机构相同会列为线索；共用信箱可以是不同的人，须逐项核对。
2. 打开一组来源，对照姓名、机构、联系方式、来源时间和名额。选择主资料、勾选实际参会身份，再确认确实同一人。每个来源可打开原资料；原始问卷、联系人、报名、联络许可和通知历史不会被覆盖。
3. 合并在 registration index 的同一次 CAS 中保存人员关联并撤回重复报名；只保留主报名的有效状态，重复名额一并释放，不在合并时自动晋升别人或寄信。原来源的邀请历史继续保留；被撤回的重复来源不再制作旧报名邀请，新确认信请从主报名处理。旧重复链接的在线确认与票券下载不再提供有效参会资格；已经加进设备的旧卡片不会被自动移除。
4. 进入「待分流」，逐人点「身份／报名」，选择一般参会者、受邀嘉宾、讲者、参展人员，可兼任。身份保存本身不确认出席、占名额或公开人物资料；既有场次／公开资料的职责须到相应安排处更改。
5. 核实本人答应出席后，可「确认出席并整合报名」；已记录答应的历史名单可沿用来源整合。若已有网站申请则关联原申请，仍按原审核状态处理。新确认出席取得名额后处理一次确认信；历史已确认者的补寄仍在报名与票券页逐笔明确操作。

「一般参会者」指以参加交流为主的人，与受邀嘉宾区分。公开报名在尚未另行分配职责时列在一般参会者，并明确显示待审核／候补／确认状态。参展商仍按公司／团队列出，一个合并后的人在组织成员统计中只计算一次。重复的源记录继续保存在原始资料工具中。

`GET /api/admin/people/duplicates` 只读返回最多 200 组线索；`POST /api/admin/people/resolve` 的 `preview` 读取来源，`roles` 与 `merge` 才写入。三个操作均要求完整活动管理权限；POST 还核对 Origin、共享会话、CSRF、来源修订和操作身份。请求上限 16 KiB，单人最多关联 100 联系人和 100 报名。没有猜测合并、批量自动清理、后台任务、新服务或新环境变量。

人员关联存于 admission 的可选 `personGroups`，与名额在同一份持久索引中；所有旧的无关联快照仍可读取。同一旧来源重新转换、并发转换、服务重启和未知 ACK 重放均沿用主报名。待审不会因合并获批，退出者不会复活。角色与合并不重写网站同意；确认信仍检查原报名许可和现行来源，任一已关联来源明确拒绝联络／出席时阻止本次通知。

## 角色视图

参展商按已有参展组织／团队排列，查看明确关联联系人与展位。旧展位仅有组织文字时保留并标示待关联，不自动建立组织或把同名组织合并。讲者／嘉宾依据已保存参与职责、逐场职责及人物关系，不将原问卷兴趣当作实际职责；同一人可同时出现于多个角色视图，出席回复与名额仍分别核对。

## 读取与权限

目录复用 person workspace 服务文件，避免增加发布包文件。授权在任何私有来源读取前执行；outreach 仅获取联系人及其许可范围的安排／关系，reviewer 仅获取报名和审核范围，组合权限才组合两种来源。列表不包含邮箱、微信、原答案、个人备注、私密确认链接或提供者配置。缺少来源明确报告不可核对，不显示成零或无关系。

分页绑定来源修订及筛选，查询字段受限。退出、401／403、换帐号、筛选或迟到回应均隔离旧资料。只读目录与角色筛选不寄信、审批、公开内容或修改任何资料。

## 确认信与 Wallet

确认名额动作之后才处理通知，初次公开申请仍待审、不寄正式邀请。沿用现有全局开关、EmailJS 模板／密钥、私有通知 journal 和每一报名唯一的通知身份；重复点击、服务重放或丢失通知 ACK 不会盲目重送。读取、刷新、开启角色名单及导入历史查看不补寄旧名单。

工作人员来源保留原 provenance／许可。联系人的当前联络许可及已核对地址必须允许本次确认通知，拒绝或缺少地址时给出原因。明确补寄入口仅对具有通知管理权限的操作者开放，缺许可、非 confirmed、已发送／未知状态不提供重复发送捷径。信件内包含私人确认页及 Apple Wallet 说明；确认页和下载仍实时核对当前名额，住宿、讲者及展位独立确认。

## 资源、验证与回退

不新增服务、依赖、环境变量、IAM、DNS 或后台扫描。继续现有 `.env.example`、香港 FC／私有 OSS 和前端 OSS；128 包文件、40 静态资源与 8 MiB 静态上限保持。只用合成人员、内存 OSS、注入邮件 provider 和隔离 Chromium，覆盖来源关联、多角色、组织／展位、分页／故障、权限与清理、明确通知及原幂等提交恢复。准确 PR／main、实际发布及 HTTPS 结果完成后补充。

尚未产生人员关联写入时可回退前一版；已有 `personGroups` 或新审计 action 后，后端须保留本阶段的索引解析与别名规则，不能直接退回不认识新字段的旧包。需要纠正错误合并时先冻结相关业务、保留备份并核对全部来源，使用兼容的修复提交；不提供一键拆分或自动复活旧名额。回退只撤回兼容界面代码，不回滚人员、原报名或通知日志，不复活旧 capability／会话，也不清除预留以重寄。备份、隔离恢复与到期删除沿用 [维护流程](maintenance-backup.md)。


本阶段合成测试覆盖同信箱不同人不自动合并、原件与历史保留、规范目录及公司成员唯一、待审不获批、重复名额释放、并发最后一席、退出不复活、原操作重放、联络许可不可继承、审核权限隔离，以及 320／390／1440px 的真实运行时浏览器流程。运行 `node --test tests/people-resolution.test.mjs tests/people-directory.test.mjs`；先构建后运行 `tests/browser/people-resolution-smoke.mjs` 和原 `unified-people-smoke.mjs`。验收均使用合成私有存储和邮件提供者，不向真实名单寄件；真实名单的逐笔核对与 iPhone 实机加入仍由主办方执行。
